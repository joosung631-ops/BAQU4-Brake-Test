# 콘 기반 직선 코스 시각화와 독립 주행 노드

대시보드 **3. 제동 테스트**는 좌우 경계, 가운데 추종 참고선과 정지열을 보여준다.
별도 `src/run.py`가 같은 인식 코드와 복사한 기존 Pure Pursuit를 사용하여
주행 명령을 계산한다. 대시보드가 주행 노드를 실행하거나 `/cmd`를 발행하지는 않는다.

## 독립 주행 실행

호스트 프로젝트 루트에서 직접 실행한다. 기존 `stop_test` 컨테이너가 실행 중이어야 한다.

```bash
bash stop_test/01_only_lidar/run.sh
```

- **`config.toml`의 `publish_cmd = false`일 때**: 인식/조향/속도/제동 판단은 실행하지만
  `/cmd` publisher 자체를 만들지 않는다. 실제 발행은 이 값을 `true`로 바꾸고 다시 실행할 때만 시작한다.
- 주행 코드·기존 C++ 알고리즘 복사본·인식 패키지·설정은 모두 `stop_test/`에 있다.
  `main/` 소스나 main 컨테이너를 읽지 않는다. 기존 ROS 이미지 공유는 소스/실행 의존성이 아니다.
- 실행할 때 코드/설정 스냅샷을 `stop_test/log/stop-test-cmd/시험ID/`에 보존하고,
  그 복사본으로 C++ 코어를 빌드한다. `commands.jsonl`에 계산한 명령과 판단 사유를 남긴다.
- 입력은 실시간 `/lidar/points`, `/gnss/odom`; 출력은 50Hz
  `std_msgs/Float32MultiArray` `/cmd`의 `[조향 raw, 속도 raw, 브레이크 0/1]`이다.
  실행 스크립트는 센서나 `trans`를 자동으로 시작하지 않는다.
- 기본 stop_test ROS 도메인은 87로 분리되어 있다. 센서와 `trans`도 같은 도메인에 있어야 한다.
  main의 센서/통신에 자동 연결하지 않는다. `/cmd` 발행자는 이 노드 하나만 사용한다.
- 기존 Pure Pursuit와 raw 변환 C++ 소스를 `src/control_core/`에 완전 복사했다.
  `source-version.json`은 원본 출처/해시 기록이며 실행 중 원본을 참조하지 않는다.
  Python 3.10용 TOML 파서는 `vendor/`에 MIT 라이선스와 함께 포함한다.

### 출발 방식 설정

`stop_test/config.toml`에서 `test_mode = true`이면 아래의 엔터 1회 출발 절차를 사용한다.
`test_mode = false`이면 엔터 대신 `startup_speed_kph`(기본 5km/h) 전진 명령을 50Hz로
계속 보낸다. 라이다·GNSS 준비 확인은 운영자가 수행하며, 수신 확인을 출발 명령의 조건으로 삼지 않는다.
명령 전송 후 새로운 유효 GNSS 측정 3회 연속으로 속도가 `min(0.5m/s, 설정 속도의 절반)`을 넘으면
추가 엔터·1초 대기·추종선 연속 확인·강제 직진 단계 없이 정상 가속 단계로 넘어간다.
GNSS 속도 공분산이 무효이거나 측정이 오래되면 이동으로 인정하지 않고 저속 명령을 유지한다.
주행에 들어간 뒤 센서 이상은 즉시 보호정지하고, 경로 미검출은 아래의 연속 프레임 기준을 적용한다.
이동 감지 전에도 사용할 수 있는 정지열 데이터의 제동과 다른 `/cmd` 발행자 검사는 유지한다.
출발 방식은 실제 명령 발행 여부인 `01_only_lidar/config.toml`의 `publish_cmd`와 별개다.
정지 후 브레이크 해제 엔터와 종료 절차는 두 모드에서 동일하다.

### 운용 절차 (test_mode = true)

`run.sh`는 대화형 터미널에서만 실행된다(`docker exec -it`). 엔터를 기다리는 동안은
항상 `brake=1`을 50Hz로 보낸다. 브레이크 보드의 PC 무수신 20초 자동 해제를 막기 위해서다.

1. `준비 완료` 안내 후 엔터 → 1초 대기. 대기 중에도 인식은 계속한다.
2. 그 시점에 가운데 선이 서로 다른 스캔에서 연속 `line_confirm_frames`번 확인되었으면 바로 주행한다.
3. 확인되지 않았으면 추가 엔터 없이 `blind_start_kph`(현재 10km/h)로
   조향 영점 직진(강제 직진)을 시작한다.
   강제 직진 중 선이 연속 확인되면 그 속도에서부터 기존 가속/유지 로직으로 넘어가고,
   다시 강제 직진으로 돌아가지 않는다. `blind_start_timeout_s` 안에 확인되지 않으면 정지한다.
   `blind_start_kph = 0`이면 안내 없이 선이 확인될 때까지 브레이크를 유지하며 기다린다.
4. 정지열 제동, 보호정지, 강제 직진 시간 초과, `q`+엔터, 첫 Ctrl-C는 모두 정지 후 사유를 출력하고
   브레이크를 유지한다. 엔터를 누르면 `/cmd`로 `0,0,0`을 2초간 보내 브레이크를 풀고 종료한다.
   GNSS 속도가 0.5m/s를 넘으면 해제를 거부한다. 속도를 알 수 없으면 경고 후 진행한다.
5. 두 번째 Ctrl-C, SIGTERM, 터미널 입력 종료는 해제하지 않고 브레이크 명령을 보낸 뒤 종료한다.

- 강제 직진 중에는 정지열 검출이 동작하지 않는다(정지열 검출도 좌우 경계가 필요하다).
  차량을 콘 앞에 정렬해 둔 상태를 전제로, 저속/짧은 시간으로만 사용한다.
- 강제 직진 중에도 점군·인식·GNSS 속도가 0.35초 넘게 끊기면 즉시 정지한다.
- 운영자 입력과 단계 전환은 `commands.jsonl`에 `kind: operator`로 기록한다.
- 대시보드 3. 제동 테스트는 새 사유(`operator_wait`, `blind_start`, `blind_start_timeout`,
  `operator_release` 등)의 한국어 문구를 아직 갖고 있지 않다. 대기 상태도 보호정지처럼 보일 수 있다.

### 속도와 제동 판단

실측 속도가 `stop_test/config.toml`의 `max_speed`에 도달하기 전에는 이 값을 목표로 한다.
한 번 도달한 후 `use_high_speed`에 따라 `high_speed`/`low_speed`로 목표를 바꾼다.
속도 명령 상승은 기본 10km/h/s로 제한한다. GNSS 속도는 도달 확인에 사용하며,
모터 RPM 변환은 기존 코어의 바퀴 지름/891.387RPM 계약을 사용한다.

반복 확인된 정지열 거리는 속도로 갱신하며, 잠깐 가려져도 보존한다.
`전방 돌출 + 정지 여유 + v*반응시간 + v²/(2*감속도)` 이내에서 브레이크를 걸고
프로세스를 재시작할 때까지 유지한다. **목표 속도 도달 전에도 제동이 우선**이다.
조향은 기본적으로 마지막 정상 주행 명령을 유지한다. 아래의 조향 복귀 옵션을 켜면
정지열 정상 제동 시 직진 영점으로 복귀한다. 기본 설정은 속도 raw=0, brake=1을 보낸다.
주행 중 점군·인식 결과·GNSS 속도가 `sensor_timeout_s`(현재 0.35초) 넘게
갱신되지 않거나 지면 추정이 명시적으로 불량이면 즉시 보호정지한다.
중복/역순 센서 타임스탬프는 신선도를 갱신하지 않는다. 알려진 bag 재생 노드나
다른 `/cmd` 발행자가 발견되어도 정지를 유지한다.

#### 경로 미검출 유예

`01_only_lidar/config.toml`의 `path_loss_stop_frames = 20`은 정상 주행 중
가운데 추종선이 **서로 다른 라이다 인식 프레임에서 연속 20번** 없을 때 보호정지한다.
10Hz에서는 약 2초이며, 50Hz 제어 타이머가 같은 스캔을 다시 읽어도 횟수는 늘지 않는다.
`test_mode` 두 모드의 정상 주행에 적용한다. 실제 모드에서 GNSS 이동을 확인했지만
아직 경로가 없으면 이 유예 동안 출발 속도·조향 영점 명령을 유지한다.

1~19프레임은 직전 조향·속도 명령을 유지하고 추가 가속은 보류한다.
경로가 한 번 복구되면 횟수를 0으로 초기화하고 정상 추종·가속을 재개한다.
20번째 미검출에서 모터 0·브레이크 1로 정지하며, 이후 경로가 복구돼도 정지는 유지한다.
미검출 횟수와 기준은 `commands.jsonl`의 `path_missing_frames`, `path_loss_stop_frames`에 기록한다.
센서 수신 중단·지면 신뢰도 실패·명령 발행자 충돌·운영자 정지는 즉시 처리하고,
유예 중에도 이미 확인한 정지열 거리의 GNSS 갱신과 제동 판단은 계속한다.
`test_mode=true`의 최초 강제 직진 시간 제한은 `blind_start_timeout_s`를 사용한다.

#### 제동 시 모터 명령 램프 감쇠

`01_only_lidar/config.toml`에서 선택한다. 기본값 `false`는 기존처럼 제동 즉시 모터 명령을 0으로 보낸다.

```toml
brake_motor_ramp_enabled = false
brake_motor_ramp_35_to_zero_s = 1.0
```

`true`이면 **정지열에 따른 정상 제동**에서 브레이크 신호는 즉시 1로 보내고,
모터 명령은 직전 주행 명령에서 일정한 감소율로 0까지 줄인다. 예를 들어 기준 시간 1초이면
35km/h 명령은 1초, 17.5km/h 명령은 0.5초에 0이 된다. 35km/h 명령에 기준 시간 0.5초를
설정하면 0.5초에 0이 된다. 실제 GNSS 속도나 실제 차량 정지 시간을 뜻하지 않는다.
주기마다 감소율은 `35 / brake_motor_ramp_35_to_zero_s` km/h/초이며,
제동 시작 후 경과 시간을 사용하므로 타이머 지연으로 감쇠 시간이 길어지지 않는다.

시간은 활성화 시 유한한 양수여야 하며, `false`일 때는 무시한다. 이전 설정처럼 두 항목이
없으면 즉시 0이 기본이다. 기존 `brake_decel_mps2`는 제동 시작 거리 계산용으로 별도로 유지된다.
램프 사용은 제동 시작 거리나 브레이크 보드의 작동 단계를 바꾸지 않는다.

센서/경로 소실, 명령 발행자 충돌, bag 재생 감지, 운영자 정지, Ctrl-C/종료에서는 램프 없이
즉시 모터 0과 brake=1을 보낸다. 정상 제동 램프 도중에도 이 조건이 생기면 감쇠를 취소하고
즉시 0을 유지하며, 센서가 복구되어도 재개하지 않는다. 최초 제동 사유는 기록에 유지한다.
감쇠 중에는 엔터로 브레이크를 해제할 수 없고, `q`+엔터로 모터 명령을 즉시 0으로 바꿀 수 있다.

실행별 `commands.jsonl`에는 `brake_motor_ramp`의 상태·시작 명령·경과 시간·취소 사유와
실제 출력 `raw`가 기록된다. 상태 전환 시 `brake_motor_ramp_active`,
`brake_motor_ramp_completed`, `brake_motor_ramp_cancelled` 이벤트도 기록한다.
설정·소스는 기존대로 실행 시 복사되어 보존된다.

램프 중에는 brake=1과 양수 모터 속도 명령을 함께 보낸다. 실제 브레이크와 모터의 반응에 따라
정지거리·부하가 달라질 수 있으며, BMS 문제 개선이나 기존 제동 성능을 보장하는 설정은 아니다.

#### 제동 시 조향 영점 복귀 옵션

`01_only_lidar/config.toml`의 `brake_steering_return_enabled`는 기본 `false`다.
꺼져 있거나 기존 설정 파일에 이 항목이 없으면 직전 조향 유지 동작이 그대로 적용된다.
`true`이면 정지열 정상 제동 시 브레이크를 즉시 켜고, 마지막 출력 조향 명령에서
직진 영점을 향해 일정한 변화율로 복귀한다. 두 출발 모드(`test_mode`)와 독립적이며,
모터 감쇠 옵션과도 독립적이다. 새로운 모터 구동 명령을 추가하지 않는다.

`brake_steering_full_left_to_zero_s`는 최대 좌측 보드 명령 `+17.01도`에서
직진 영점 `steering_zero_deg`까지 이동하는 기준 시간이다. 기본값은 1.0초이며,
활성화 시 유한한 양수여야 한다. 복귀 변화율은 `(17.01 - steering_zero_deg) / 기준 시간` 도/초다.
현재 `steering_zero_deg = 0.0`에서는 1초 설정 시 좌우 모두 17.01도/초로 복귀한다.
8.505도에서 시작하면 0.5초, 2도에서 시작하면 약 0.118초가 걸리며 영점을 넘지 않는다.
영점 보정이 있으면 그 값을 유지한 직진 명령으로 복귀하므로 최종 raw 조향이 0이 아닐 수 있다.

복귀는 제동 시작 시 마지막 출력값을 기준으로 하며, 출력 범위를 넘었던 추종 계산값은
실제 전송 범위로 제한해 사용한다. 타이머 횟수 대신 실제 경과 시간으로 계산한다.
설정 시간은 목표 명령의 복귀 시간이며 실제 바퀴 도달 시간이나 회전 억제 효과를 보장하지 않는다.

센서/경로 이상, 명령 발행자 충돌, bag 재생, 사용자 정지, Ctrl-C/종료에서는 자동 복귀를
시작하지 않는다. 정상 복귀 도중 이런 조건이 발생하면 현재 조향 명령에서 중단하며,
센서가 복구돼도 재개하지 않는다. 브레이크 ON과 기존 보호정지 시 모터 0 처리는 유지한다.
복귀 중에는 엔터로 브레이크를 해제할 수 없다. `q`+엔터는 복귀를 중단하고 브레이크를 유지한다.

`commands.jsonl`의 `brake_steering_return`에 상태, 시작각, 현재 명령각, 영점,
기준 시간, 변화율, 경과 시간, 취소 사유를 기록한다. 상태 전환 이벤트는
`brake_steering_return_active`, `brake_steering_return_completed`,
`brake_steering_return_cancelled`로 기록한다.

#### 완전 정지 후 최고속도·변위 그래프

`run.sh` 실행 중 제동 명령 이후 유효한 GNSS 속도가 **0.1m/s 이하로 0.5초 이상** 유지되고
모터 명령이 0이 되면, 터미널에 해당 주행의 GNSS 최고속도를 출력한다. 중복 GNSS 시각,
무효 속도 공분산, 센서 공백은 정지 확인 표본으로 사용하지 않는다. 모터 명령 0이나
제동 시작만으로 완전 정지했다고 판단하지 않는다.

호스트의 `01_only_lidar/ouput/YYMMDD_HHMMSS/run_summary.png`에 그래프 세 개를 한 이미지로
저장한다. `ouput`은 요청한 디렉터리 이름이다. 예: `ouput/261030_003735/`.
폴더 이름은 **한국 시간의 완전 정지 확인 날짜·시각**이며, 같은 초의 결과가 있으면 `_01` 등으로
구분하여 덮어쓰지 않는다. 이미지를 만들기 위해 브레이크를 해제하거나 프로그램을 종료할 필요가 없다.

- 공통 x축: 출발 시 GNSS 위치에서 초기 진행방향으로 투영한 전방 변위(m).
  초기 방향은 첫 1m 이상의 GNSS 이동으로 정한다. 짧은 주행은 가능한 이동 방향을 사용하고
  `summary.json`에 제한을 남긴다. 누적 주행거리나 시간 축이 아니다.
- 그래프 1: GNSS 실측 속도(km/h), 모터 목표 속도, 해당 주행 최고속도.
- 그래프 2: 매 스캔에서 검출한 개별 콘의 라이다 기준 전방 거리(m), 정지열 후보/확인 거리(m).
  정지열 거리는 코스 방향 기준이다. 제어기의 거리 추정값으로 대체하거나 미검출을 0으로 채우지 않는다.
- 그래프 3: 각 위치에서 발행한 `/cmd[1]` 모터 raw와 `/cmd[2]` 브레이크 0/1.
  동일 위치에서 바뀐 명령은 겹쳐 보일 수 있다. 정확한 명령 순서는 `samples.csv`의 시각으로 확인한다.

변위는 GNSS 위치를 사용하고, 명령/스캔 위치는 짧은 GNSS 표본 간격 안에서 보간한다.
센서 공백을 가로질러 보간하지 않으며, GNSS 위치나 콘 데이터가 없으면 빈 구간으로 표시한다.
`publish_cmd=false`이면 이미지에 모의 실행이라고 표시하며 실제 전송값으로 해석하지 않는다.
브레이크 값은 명령 기록이며 물리적 작동 피드백이 아니다.

결과 폴더에는 PNG 외에 원본 `report.json`, 설정·최고속도·좌표 기준을 담은 `summary.json`,
GNSS/명령 `samples.csv`, 콘/정지열 `cones.csv`도 저장한다. 기존 실행 증거 폴더에도
`report.json`이 남는다. GNSS로 완전 정지를 확인하지 못하고 종료하면 정상 정지 보고서를 만들지 않는다.

보고서 수집은 제어와 분리되어 있고, 이미지 생성은 호스트 Python의 별도 프로세스에서 수행한다.
호스트에 `matplotlib`이 필요하며 `run.sh`가 출발 전에 확인한다. 한글 폰트가 없으면 영문 축 제목을 사용한다.
이미지 저장 실패는 제동 명령을 변경하지 않으며, 남은 `report.json`으로 재생성할 수 있다.

```bash
python3 stop_test/01_only_lidar/src/run_report.py \
  --job stop_test/log/stop-test-cmd/<실행 폴더>/report.json \
  --output-root stop_test/01_only_lidar/ouput
```

더 멀리서 제동하려면 `01_only_lidar/config.toml`의 `stop_margin_m` 또는 `reaction_s`를
키우거나, `brake_decel_mps2`를 줄인다. 감속도는 거리 계산용 가정이며 실제 브레이크
강도를 바꾸지 않는다. 예를 들어 여유 6m/반응 0.3초/감속도 5m/s²/전방 돌출 1.438m에서는
15km/h의 제동 시작 거리가 라이다 기준 약 10.42m다. 여유 2m일 때의 약 6.42m보다
4m 일찍 시작한다. 정지열 반복 확인이 먼저 필요하며, 센서/경로 소실은 거리와 무관하게
보호정지를 시작한다. 설정과 코드는 실행 시 복사하므로 변경은 다음 명시적 실행부터 적용된다.

현재 장착 좌표와 조향 영점, 감속도/반응시간 가정은 실차 제동 성능 보장값이 아니다.
**35km/h에서의 실제 정지거리나 목표 속도 달성을 검증한 값이 아니다.**
`trans`의 실제 송신 모드와 ASMS AUTO 권한도 별도로 필요하다.
정상 Ctrl-C/SIGTERM에서는 정지 명령을 보낸다. 강제 종료/통신 단절 때의 물리적 정지는
차량측 watchdog/비상정지가 담당해야 한다.

## 화면과 데이터

### 실시간 주행 상태

제동 테스트 화면 상단에 현재 GNSS 속도, 가속 요청, 최고 목표 속도 도달 이력,
제동 명령, 현재 단계의 목표 속도/램프 적용 후 속도 명령과 판단 사유를 표시한다.
상단 상태에는 `정지선 인식 · 제동 거리 대기`, `정지선 제동 시작 · 명령 유지`,
`보호정지 · 제동 명령 유지`를 구분한다. 정지선까지의 거리는 주행 노드가 확인한 뒤
속도로 갱신한 라이다 기준 추정치이며, 제동 시작 거리와 비교해 표시한다.
제동이 시작되면 그때의 기준 거리와 최초 정지 사유를 유지한다. 이후 경로가 사라져도
정지선 제동을 보호정지로 바꿔 표시하지 않는다. 제동 명령 발행은 보드 수신이나
실제 제동력 확인을 뜻하지 않는다. 시각화 화면의 정지선 후보와 주행 판단은 별도다.
`가속 요청`은 제동하지 않고 속도 명령이 실측보다 0.5km/h 넘게 높을 때이며,
실제 가속도나 하드웨어 제동 피드백을 뜻하지 않는다. 최고 목표 도달은 기존 제어기의
`max_speed` 실측 도달 판정을 그대로 표시하고 실행 중 유지한다.

`publish_cmd=false`이면 모의 계산임을 명시한다. 주행 노드를 실행하지 않아도
실시간 수집기의 유효 GNSS 속도는 표시하며, 나머지는 확인 불가로 둔다.
주행 노드의 속도가 오래되면 과거 값을 표시하지 않는다. 라이다가 끊겨도 계속
수신되는 제동/오류 상태는 표시하고, 상태 전송이 0.7초 이상 끊기면 제거한다.
bag 보기에는 실시간 주행 상태를 섞지 않는다. 변경한 상태 전송은 다음 주행 노드
실행부터 적용된다. 대시보드는 주행 노드를 자동 실행하지 않는다.

실시간 영상은 `/lidar/points`, `/camera/image_raw/compressed`, `/gnss/fix`,
`/gnss/odom`을 수집한다. 수집기는 main 컨테이너의 ROS 도메인(기본 0),
독립 stop_test는 기본 87이므로 각 노드가 실제 입력 센서와 같은 도메인인지 확인한다.
이 수정은 운영 중인 ROS 도메인이나 센서/통신 실행 설정을 변경하지 않는다.
상태 패킷도 기존 웹 전송량 제한(본문 합산 250kB/s)을 공유한다.

격리 ROS 도메인 175에서 기록 스캔/카메라를 테스트 토픽으로 발행하여
실제 ROS 구독 → 인식/제어 계산 → HTTP/웹소켓 → Chromium 화면을 검증했다.
센서 대기·가속·35km/h 도달·정지열 제동·점군 소실·상태 만료·bag 전환을 확인했고
`/cmd` 발행자는 0개였다. 이는 실차 주행 시험이 아니다.
기록은 `test_runs/dashboard-drive-status-20261027/`에 보존한다.

### 조향 예상 진행선

대시보드 상단 LiDAR 화면의 `예상 진행선`에서 노란 중심선, 얇은 차폭 참고선,
현재 차량 윤곽과 진행 방향 화살표를 두 3D 화면에 겹쳐 표시한다.
`가상 조향`에서는 슬라이더로 각도를 바꾼다(+좌/-우). 슬라이더는 표시만 변경하며
주행 노드·설정·`/cmd`를 변경하지 않는다. `0°`로 표시 각도를 초기화한다.

`주행 계산값`에서는 독립 stop_test 노드가 계산한 명령을 표시한다.
실제 발행을 꺼 둔 경우에도 표시할 수 있다. 노드를 다시 실행하면 표시 데이터 전송이 시작된다.
`prediction_url`로 최대 10Hz의 숫자 정보만 비동기 전송한다. 대시보드 연결 실패는
제어 계산을 막거나 바꾸지 않는다. 서로 다른 ROS 도메인에서도 host loopback HTTP로 전달한다.
입력은 localhost의 표시 전용 `/api/brake/prediction`이며 제어 명령을 실행하는 API가 아니다.
대시보드는 현재 live 점군 시각과 0.5초 이내로 대응되는 자료만 사용하고,
0.7초 이상 갱신이 없으면 제거한다. bag 보기에는 live 계산값을 겹치지 않는다.
따라서 대시보드의 실시간 LiDAR 수집기도 주행 노드와 같은 센서 자료를 받아야 한다.
숫자 표시 데이터가 다른 ROS 도메인을 넘어 전달되어도, 대시보드에 해당 점군이 없으면
계산값 예상선을 그리지 않는다. 주행 ROS 도메인을 바꾸면 보기 수집기의 도메인도 맞춰야 한다.

모델은 고정 조향·무슬립 자전거 모델 `곡률=tan(등가 조향각)/축간거리`다.
공통 축간거리 1.328m/차폭 1.280m/조향 모델 ±17.01°를 사용하며,
계산값 모드에서는 실행 설정의 조향 영점과 LiDAR 장착 보정을 반영한다.
가상 조향은 명목 장착 위치 x=0.559m/y=0m/방향 보정 0°를 사용한다.
노란 선은 앞으로 10m를 주행한다는 가정의 기하 참고선이다. 제동 중에는 조향 방향 참고이며
시간별 실제 이동 거리 예측이 아니다. 얇은 선은 후륜축 위치의 차폭 참고이며 충돌 여유 보장이 아니다.
기존 5~12km/h 원선회 시험은 좌우 차이가 있었고 중간각 선형성·조향 지연·슬립·35km/h
궤적은 검증하지 않았다. 화면을 실제 주행 궤적의 보장값으로 해석하지 않는다.

- 위쪽 바닥 제거 점군과 아래쪽 콘 3D 화면 모두에 선을 겹친다.
- 좌측 경계는 파랑, 우측 경계는 보라, 가운데는 초록이다.
  정지열 후보는 주황 점선, 여러 스캔에서 반복 확인된 정지열은 빨강 실선이다.
  반복 확인은 같은 위치의 관측이라는 뜻이며 실제 제동 요구나 콘 분류 확정이 아니다.
- `선 표시`로 네 선을 함께 켜거나 끈다. 회전·확대는 기존 두 화면에서 연동한다.
- 아래쪽 `코스 확대`는 현재 관측된 선 범위에 맞춰 두 3D 화면을 확대한다.
- 카메라와 GPS는 함께 유지한다. rosbag 직접 읽기와 실시간 구독이 같은 추출기를 사용한다.
- 검출 조건이 부족하면 없는 선을 그리지 않는다. 한쪽만 보이면 관측한 경계만 표시한다.
  평행·폭·겹치는 구간 조건이 부족하거나 비슷한 복수 코스가 있으면 가운데와 정지선을 보류한다.
- 입력 전환·seek·오류·오래된 검출에서는 이전 선을 지운다.
- 좌우/가운데 선과 근거리 형상 기반 정지선은 콘 검출과 같은 스캔에서 최대 5Hz 추출한다.
  원거리 정지열은 원본 점군마다 최대 10Hz 검사하고, 최근 0.35초 이내의 경계만 재사용한다.
  점군 디코딩과 같은 스캔의 지면 적합은 시각화/콘 검출/원거리 검출에서 공유한다.
  원본 점군에서 검출한 최대 64개의 가까운 콘을 사용한다. 화면용 축소 점군에서 찾지 않는다.
- 전송은 기존 네 선의 3D 양 끝점에 최대 51바이트, 원거리 정지열의 상태/거리/
  지지 셀/관측 폭/양 끝점에 최대 21바이트를 사용한다. 지지 셀 개수는 콘 개수가 아니다.
  기존 전체 접속자 합산 250,000B/s, burst 32,000B 예산을 유지하고 영상은 남는 예산을 쓴다.
  선·상자·상태용 예약은 20,000B/s이며, 1시간 본문 상한은 900,032,000바이트다.
  이는 통신사 계측량이 아니며 TCP/SSH/재전송은 별도다.

## 추출 방법

기존 `ConeDetector`의 지면 제거·거리 적응형 군집화·콘 형상 필터를 그대로 사용한다.
검출 중심을 원본 `os_lidar` 좌표에서 명목 전방 `-X`, 명목 좌측 `-Y`로 해석한다.
**차량 `base_link` 보정이 된 좌표는 아니다.**

1. 콘 두 점으로 만드는 직선 중 전방과 20도 이내인 가설들을 검사한다.
   무작위 RANSAC 대신 최대 64개 콘의 쌍을 열거하는 결정적 합의 방식이다.
2. 직선까지 22cm 이내의 콘을 모으고 총최소제곱(TLS)으로 방향을 다시 추정한다.
   콘 3개 이상, 관측 길이 4m 이상을 요구한다. 길이 방향으로 8m 넘는 공백은 이어 붙이지 않는다.
3. 두 경계의 방향 차이가 6도 이내인지 확인한다. 두 줄 내부의 공분산으로 공통 방향을 구하고
   각 줄의 중앙값 오프셋으로 두 평행선을 만든다. 폭 2~8m, 센서 원점에서 양쪽 각각 0.8m 이상,
   앞뒤 관측 구간이 4m 이상 겹치는 조건을 요구한다.
4. 양쪽 오프셋의 평균이 가운데 참고선이다. 두 경계가 모두 실제로 관측된 앞뒤 범위만 그린다.
   직선 가정을 사용하므로 곡선 코스용 경로 생성기가 아니다.
5. 경계 사이 콘에서 공통 진행 방향과 직각에 가까운 줄을 찾는다. 직각에서 20도 이내,
   줄까지 오차 28cm 이내, 콘 3개 이상을 요구한다.
   **양쪽 경계에서 각각 45cm 이상 안쪽인 콘이 최소 2개** 있어야 한다.
   일반적인 좌우 경계 콘 한 쌍으로 가로 정지선을 만들지 않는다.
6. 가로줄이 코스 폭의 60% 이상을 덮고, 양 끝의 빈 폭은 각각 `max(0.65m, 폭의 20%)` 이하,
   관측 콘 사이 최대 가로 간격은 2m 이하여야 한다.
   경계가 함께 관측된 끝보다 최대 2.5m까지만 가로줄을 탐색한다.
   복수 가로줄이 있으면 가장 가까운 유효 후보를 표시한다.
7. 정지선 후보가 있으면 경계와 가운데 선을 그 선까지만 표시한다. 이는 표시 자르기이며
   차량 앞 범퍼·정지 여유를 반영한 실제 정지 지점이 아니다.

모든 선의 높이는 같은 스캔에서 추정한 지면 평면에 놓고 화면 가독성을 위해 8cm 올린다.
따라서 3D로 회전해도 경사진 지면을 따른다. 콘의 머리나 관측 상자 중심을 서로 잇는 선은 아니다.
위 형상 기반 가로선은 항상 단일 스캔의 기하 후보다. 아래 보조 검출의 반복 확인은
별도 상태이며 신뢰도 확률을 계산하지 않는다.

## 원거리 정지열 보조 검출

닫힌 직선 코스 안에 바닥과 콘만 있다는 시험 가정을 사용한다. 가까운 좌우 경계가
`paired`일 때만 검사하며, 모호한 경계/한쪽 경계/0.35초 넘은 경계에서는 보류한다.
가까운 경계를 45m까지 연장하는 가정이며, 가운데 추종선 자체를 그 거리까지 늘리지는 않는다.

1. 원본 점군을 코스 방향/횡방향으로 투영한다. 양쪽 경계에서 각각
   `max(0.45m, 코스 폭의 12%)` 안쪽, 전방 2~45m를 검사한다.
2. 가까운 2~18m 내부에서 지면 ±7cm 이내 반사점 80개 이상, 비율 35% 이상,
   2m 길이 셀 4개 이상의 지지를 요구한다. 지면을 20cm 낮게 잡아 바닥을 장애물로
   바꾸는 합성 반례는 이 검사에서 보류된다. 먼 노면의 경사까지 보장하는 검사는 아니다.
3. 지면 위 15cm~1.05m 반사점을 35cm XY 셀로 묶는다. 깊이 60cm인 횡방향 띠에서
   서로 다른 횡방향 셀 3개 이상, 관측 폭 `max(1.5m, 코스 폭의 40%)` 이상을 요구한다.
   띠 경계의 누락을 줄이기 위해 30cm 어긋난 두 배치를 검사한다.
   개별 콘의 관측 높이 차/점 개수/ring 수를 요구하지 않는다.
4. 가장 가까운 유효 띠를 후보로 표시한다. 선의 양 끝은 실제 지지점의 횡방향 범위이며,
   높이는 표시를 위해 해당 스캔 지면 위 12cm에 놓는다. 지지점이 콘 3개라는 뜻은 아니다.
5. 최근 서로 다른 스캔 3개 중 2회 관측되고, 시간 차 0.35초 이내이며,
   `/gnss/odom` 속도로 예상한 거리 변화와 70cm 이내로 맞으면 반복 확인한다.
   경계 방향 차 6도/횡방향 중심 차 75cm도 검사한다. 속도는 점군 시각에서 0.30초
   이내 자료만 사용한다. rosbag은 기록 시각, 실시간은 수신 시각을 사용한다.
6. 일시정지한 한 스캔을 다시 계산해도 확인 횟수는 늘지 않는다. seek/입력 전환/잘못된
   점군에서는 이력을 지운다. 후보가 없는 최신 스캔에서는 선을 유지하지 않는다.

원거리 후보가 있으면 화면의 가로선에 우선 표시한다. 원거리 후보가 없고 기존 형상 기반
가로선만 있으면 주황 점선으로 표시한다. 거리·지지 셀·폭은 화면에 별도로 표시한다.
거리는 명목 코스 방향의 센서 기준 거리이며, 앞 범퍼 여유 거리가 아니다.
출발 전부터 보일 수 있으므로 발견 즉시 제동하는 로직과 연결하면 안 된다.

## 간격·오검출·누락에 관한 제한

- 위 숫자는 **현재 소프트웨어 표시 조건**이다. 대회 배치 규정이나 실차 보장값이 아니다.
- 콘이 너무 가까우면 기존 점 군집 단계에서 하나로 합쳐져 콘 형상 필터에서 탈락할 수 있다.
  점과 점의 연결 반경은 `min(0.48, 0.20 + 0.012 × 거리[m])`m로, 10m에서 32cm,
  20m에서 44cm, 약 23.3m 이후 48cm다. 이것은 **콘 중심 간 안전 간격이 아니라
  관측 표면 점 사이 연결 거리**다. 콘 바닥 크기·가림·점 분포 때문에 하나의 중심 간 최소 간격을
  보장할 수 없으며 실제 배치로 검증해야 한다.
- 너무 멀리 떨어진 콘, 먼 거리의 희박한 점, 가림 때문에 콘이 빠져도 경계/가로줄이 누락된다.
  가로줄에서 콘 하나가 안 보이면 관측 간격이 2m를 넘어 빨간 선이 사라질 수 있다.
  실제 기록에서 약 1.7m의 관측 간격이 있어 초기 1.6m 기준은 누락을 만들었고 2m로 조정했다.
- 콘처럼 검출된 시설물들이 평행한 두 줄 또는 가로줄을 이루면 오검출할 수 있다.
  기하만으로 실제 콘·코스 끝·차량이 통과할 수 없는 벽을 확정할 수 없다.
- 폭 변화·곡선·큰 초기 방향 차이·코스 밖 다른 콘줄·측면 잡음은 잘못된 경계 선택 또는 선 보류를 만든다.
  센서가 코스 중간에 있다는 가정을 쓰며 원점 양쪽 여유 조건은 차량 전체의 충돌 여유 검사가 아니다.
- 원거리 후보는 스캔 사이 거리 변화를 확인하지만 점군 deskew/전역 누적은 하지 않는다.
  검출 구성이 바뀌면 선이 흔들리거나 잠깐 사라질 수 있다.
  정지선에 아주 가까워져 경계 관측 길이가 4m 미만이 되면 가로줄이 보여도 선을 보류할 수 있다.
  향후 실제 제동 연결에서는 검증한 제동거리와 별도의 제동 상태 유지가 필요하다.
- 후진·정지 중에도 기하 선은 표시된다. 후보 표시가 전진 중 제동 요구를 뜻하지 않는다.
- 원본 센서 축·장착 각도·시각 동기화는 아직 주행 제어용 검증이 필요하다.
  마지막 프레임을 50Hz로 반복 계산해도 새 센서 관측이 생기지는 않는다.

## 코드와 검증

원본 추출기는 `stop_test/src/lidar_cone/lidar_cone/course_lines.py`이며 ROS에 의존하지 않는다.
기존 소스 반입 방식에 맞춰 같은 파일을 main의 콘 패키지에도 복사했다.
원거리 보조 검출/반복 확인은 같은 패키지의 `stop_row.py`가 담당하며 main에도 동일하게 복사한다.
`main/tools/brake_geometry.py`가 추출기를 호출하고 dashboard의 `brake.py`/`brake.js`가
전송·표시한다. 두 패키지의 추출기 SHA256이 같은지 시험 기록에서 확인한다.

검증 자료는 호스트 `test_runs/dashboard-brake-lines-20261027/`에 보존한다.
합성 장면의 오검출 방지 테스트, ROS 메시지부터 선 추출까지의 통합 테스트,
웹 전송·초기화 테스트, 실제 Chromium의 WebGL 색상·영상·GPS·전환 검증을 포함한다.
과거 낮/밤 9개 bag의 4,297개 콘 검출 프레임도 재생했다.
이는 프레임별 검출 가능 여부 확인이며, 전수 정답 라벨에 대한 정확도·재현율 측정은 아니다.
과거 콘 검출 자료는 30m ROI이고 현재 대시보드는 45m ROI이므로 동일한 검출 목록을 보장하지 않는다.

원거리 보조 검출 적용 자료는 `test_runs/dashboard-early-stop-20261027/`에 보존한다.
9개 기록의 원본 4,297스캔을 CPU 8개 작업으로 검사하고, 경계 5Hz/100ms 지연 모형도
별도로 비교한다. 이 모형에서 낮 기록 하나는 36m에서 24m로 확인이 늦어졌으므로
오프라인 최대 검출 거리를 실시간 보장 거리로 사용하면 안 된다.
